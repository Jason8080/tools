为什么选择 SseIm Framework?

基于 Spring Boot WebFlux + SSE 的配置驱动即时通讯框架。3 行 YAML 配置，零 Java 代码即可获得实时消息推送能力。

💡
框架定位

SseIm Framework 是即时通讯的基础设施，专注于消息的实时推送。它解决"如何把消息从服务端实时推送到客户端"，提供可插拔的 MQ 桥接和 SSE 推送能力。

⚙

配置 application.yml

3 行配置定义端点，框架自动完成端点注册、Stream 绑定、SSE 连接管理：

YAML

  endpoints:
    - path: /api/chat/push
      topic: im.chat
      mode: push          # POST 接收消息 → 发送到 MQ

    host: localhost
    port: 5672

决策原因收益
路径与 Topic 解耦 URL 是对外契约，Topic 是内部实现。两者独立演进，互不影响。 URL 可以 RESTful 化、版本化；Topic 可以按业务语义命名

URL 路径是对外契约，可以随意设计（RESTful、版本化）；Topic 是内部实现，可以随意命名。两者互不影响，独立演进。

自动创建链路

启动时，EndpointAutoConfiguration 自动完成以下工作：

阶段组件动作
1 EndpointRegistry 注册端点配置（path → topic + mode）
2 TopicFactory 按需创建 Stream binding（输出或输入）+ Consumer Bean
3 TopicRegistry 按需创建 Publisher / Repeater / Subscriber 组件
4 EndpointRouter 构建 RouterFunction，动态路由请求到 PUSH / PULL 处理器

SPI 扩展点

零侵入扩展，按需渐进式自定义。

1. Factory 模式（组件级自定义）

通过工厂模式替换默认实现：

Java 
// 1. 继承骨架类
public class ChatPublisher extends ImPublisher {
    public ChatPublisher(String topic, Supplier<Repeater> repeaterSupplier) {
        super(topic, repeaterSupplier);
    }

    @Override
    public Serializable push(MultiValueMap<String, String> urlParams, Msg msg) {
        log.info("[ChatPublisher] 推送聊天消息");
        return super.push(urlParams, msg);
    }
}

// 2. 实现工厂
@Component
public class ChatPublisherFactory implements PublisherFactory {
    @Override
    public Publisher create(String topic, Supplier<Repeater> repeaterSupplier) {
        if ("im.chat".equals(topic)) {
            return new ChatPublisher(topic, repeaterSupplier);
        }
        return null; // 其他 Topic 使用默认实现
    }
}

2. RepeaterInterceptor（消息拦截器）

拦截消息流的关键节点，用于审计、持久化、历史回放：

Java 
@Component
public class RedisReplayInterceptor implements RepeaterInterceptor {
    @Autowired
    private RedisTemplate<String, byte> redisTemplate;

    @Override
    public Mono<Boolean> beforeSend(TopicMessage<Msg> message) {
        // 发送前持久化到 Redis
        redisTemplate.opsForList().rightPush(key(message.getTopic()), serialize(message));
        return Mono.just(true); // false 拦截消息
    }

    @Override
    public Flux<Msg> transformSubscribeStream(String topic, Flux<Msg> stream, ...) {
        // 订阅时先回放历史消息
        Flux<Msg> history = loadFromRedis(topic);
        return Flux.concat(history, stream);
    }
}

3. AccessFilter（端点访问控制）

Pipeline-Filter 模式的安全扩展：

Java 
@Component
@Order(10)
public class JwtAuthFilter implements AccessFilter {
    @Autowired
    private JwtService jwtService;

    @Override
    public void doFilter(AccessContext context, AccessFilterChain chain) {
        String token = context.getHeader("Authorization")
                .filter(h -> h.startsWith("Bearer "))
                .map(h -> h.substring(7))
                .orElseThrow(() -> new AccessDeniedException("Missing token", HttpStatus.UNAUTHORIZED));

        UserDetails user = jwtService.validate(token);
        context.setPrincipal(user);
        chain.doFilter(context);
    }
}

完全自定义 Repeater（绕过 MQ）

Java 
public class DirectRepeater implements Repeater {
    @Override
    public Serializable send(TopicMessage<Msg> message) {
        // 直接推送到 Redis Pub/Sub，绕过 MQ
        redisTemplate.convertAndSend(message.getTopic(), serialize(message));
        return message.getId();
    }

    @Override
    public void receive(TopicMessage<Msg> message) {
        // 从 Redis 接收后推送到 SSE
        sseConnectionManager.publish(message.getTopic(), message);
    }

    @Override
    public Flux<Msg> subscribe(MultiValueMap<String, String> urlParams) {
        // 从 Redis 订阅实时流
        return redisReactiveTemplate.listenToChannel(topic()).map(this::deserialize);
    }
}

定向投递

将消息精准送达指定用户，而非广播给所有人。框架内置双通道架构，O(K) 精准投递，零额外依赖。

设计洞察

传统的定向投递模型：每条连接挂一个 filter，广播消息到来时 N 个连接各自判断「这消息是不是给我的」。复杂度 O(N)。

框架采用双通道互斥架构：把路由决策从接收端推到发布端，拆分为两条结构性互斥的通道——广播通道（topicSink）和定向通道（directedSink）。连接在创建时就决定走哪条通道，消息到达时无需 filter，复杂度从 O(N) 降为 O(1) + O(K)，K 为目标连接数。

💡
核心洞察

双通道互斥是结构性的：广播连接根本没有 directedSink，定向连接不订阅 topicSink 的广播消息。两条通道在创建时就分岔，不可能重复投递。因此 filter 这个概念完全消失——不是优化了 filter，而是让 filter 变得没有必要。

核心概念

定向投递建立在一个对称模型上：身份（Identity）与意图（Intent）。

概念载体语义类比
身份（Identity）ConnectionMetadata.routingKey「我是谁」— 订阅方声明自己的身份标识信封上的寄件人
意图（Intent）TopicMessage.routingKeys「送给谁」— 发布方指定投递目标的集合信封上的收件人

匹配规则：当消息的某个 routingKeys 元素等于连接的 routingKey 时，消息投递到该连接。routingKeys 为空 → 广播，所有连接收到。非空 → 定向，仅匹配的连接收到。

路由键机制

身份建立

定向投递的前提是：每个 SSE 连接都有明确的身份标识（routingKey）。框架通过四层提取自动完成，优先级从高到低：

优先级来源适用场景示例
① AccessFilter 设置的 principal（String 类型） 生产环境 — JWT / OAuth 认证 JWT Filter 解析 token → setPrincipal(userId)
② PrincipalRoutingKeyConverter 从复杂 principal 提取 principal 为非 String 对象（如 UserDetails） 从 UserDetails 提取 getUsername()
③ X-Me 请求头 服务端调用、Postman 测试、fetch-based SSE curl -H 'X-Me: alice' ...
④ 从 URL 参数按 routing-keys 配置组合 浏览器 EventSource（无法自定义请求头） EventSource('/api/chat/pull?tenant=acme&room=lobby')
⚠️
安全提示

URL 参数（?tenant=acme&room=lobby）和请求头（X-Room）均为纯声明，无认证能力。适用于开发调试。生产环境应通过 AccessFilter 实现 JWT 等认证机制，确保身份不可伪造。

路由键格式

routingKey 格式为规范化查询字符串：key 按字母排序，key=value 以 & 拼接，值取 getFirst()。保证参数顺序无关性：

?tenant=acme&room=lobby  →  "room=lobby&tenant=acme"（key 字母排序）
?room=lobby&tenant=acme  →  "room=lobby&tenant=acme"（相同结果，顺序无关）
?room=lobby              →  "room=lobby"（单键）
无参数                    →  null（广播连接，不参与定向索引）

配置方式

框架支持两级配置：全局默认 + 端点级覆盖。

YAML 
im:
  sse:
    routing-keys: [room]       # 全局默认（按房间路由）
  endpoints:
    - path: /api/chat/pull
      topic: im.chat
      mode: pull               # routingKeys 未设置 → 继承全局 ["room"]
    - path: /api/chat/push
      topic: im.chat
      mode: push               # 继承全局 ["room"]，与订阅方保持一致
    - path: /api/room/pull
      topic: im.room
      mode: pull
      routing-keys: [tenant, room]  # 端点覆盖：多租户聊天室
    - path: /api/room/push
      topic: im.room
      mode: push
      routing-keys: [tenant, room]  # 必须与对应的 pull 端点配置一致

routing-keys 语义：

  • null / 未配置 / [] — 全部 URL 参数参与（默认）
  • ["*"] — 显式全部参数（等价于 null）
  • ["room"] — 指定字段（仅提取 room 参数）
  • ["tenant", "room"] — 指定多字段（多租户场景）

对称语义与匹配规则

同一套 RoutingKeyComposer 同时用于订阅方的身份建立和发布方的目标提取，保证双方寻址语义一致：

  • 订阅方（PULL）：从 URL 参数提取路由标识作为连接身份（如 ?tenant=acme&room=lobby → routingKey = "room=lobby&tenant=acme"）
  • 发布方（PUSH）：从 URL 参数提取路由标识作为投递目标（如 ?tenant=acme&room=lobby → targets = {"room=lobby&tenant=acme"}）
⚠️
匹配规则

同一 Topic 的订阅方和发布方必须使用相同的 routing-keys 配置，确保 routingKey 格式一致。例如：订阅方用 ["tenant", "room"]，发布方也必须用 ["tenant", "room"]。可通过全局 im.sse.routing-keys 统一配置，或通过 EndpointProperties.routingKeys 按端点覆盖（但同一 Topic 的 PUSH/PULL 端点必须保持一致）。

路径 B — Java API（服务端内部调用）

在 Java 代码中直接构建 TopicMessage，设置 routingKeys 字段：

Java 
@Autowired
private TopicRegistry topicRegistry;

// 定向投递到指定房间 — routingKey 格式需与订阅方一致
// 订阅方：?tenant=acme&room=lobby → routingKey = "room=lobby&tenant=acme"
public void sendToRoom(String tenant, String room, ChatMsg msg) {
    String target = "room=" + room + "&tenant=" + tenant;
    TopicMessage<ChatMsg> envelope = TopicMessage.<ChatMsg>builder()
            .topic("im.room")
            .msg(msg)
            .routingKeys(Set.of(target))     // 定向投递
            .build();
    topicRegistry.ensureRepeater("im.room").send(envelope);
}

// 批量定向 — 投递到多个房间
public void sendToRooms(Set<String> rooms, ChatMsg msg) {
    Set<String> targets = rooms.stream()
            .map(room -> "room=" + room)
            .collect(Collectors.toSet());
    TopicMessage<ChatMsg> envelope = TopicMessage.<ChatMsg>builder()
            .topic("im.chat")
            .msg(msg)
            .routingKeys(targets)
            .build();
    topicRegistry.ensureRepeater("im.chat").send(envelope);
}

扩展点

框架提供两个 SPI 扩展点，支持自定义路由键组合逻辑和身份提取逻辑。

自定义路由键组合器（RoutingKeyComposer）

默认实现 DefaultRoutingKeyComposer 按规范化查询字符串格式组合（key 字母排序）。如需自定义格式（如 HMAC 签名、自定义拼接规则），可实现 RoutingKeyComposer 接口：

Java 
@Component
public class SignedRoutingKeyComposer implements RoutingKeyComposer {

    @Override
    public String composeRoutingKey(List<String> routingKeys, MultiValueMap<String, String> params) {
        // 自定义逻辑：如 HMAC 签名
        String raw = buildRawKey(routingKeys, params);
        return raw + "&sig=" + hmacSign(raw);
    }

    @Override
    public Set<String> extractRoutingTargets(List<String> routingKeys, MultiValueMap<String, String> params) {
        // 需与 composeRoutingKey 保持寻址语义一致
        // 即：发布方的 target 等于订阅方的 routingKey 时，消息投递到该连接
    }
}

注册为 Spring Bean 后，框架自动发现并使用，替代默认实现（通过 @ConditionalOnMissingBean 保证）。

自定义 Principal 转换器（PrincipalRoutingKeyConverter）

当 AccessFilter 设置的 principal 为非 String 类型（如 UserDetails、JwtUser）时，框架通过 PrincipalRoutingKeyConverter 将其转换为 routingKey：

Java 
@Component
public class UserDetailsRoutingKeyConverter implements PrincipalRoutingKeyConverter {

    @Override
    public boolean supports(Class<?> principalType) {
        return UserDetails.class.isAssignableFrom(principalType);
    }

    @Override
    public String convert(Object principal, AccessContext context) {
        return ((UserDetails) principal).getUsername();
    }
}

多个转换器按 getOrder() 排序依次尝试，首个 supports() 返回 true 且转换结果非空的转换器获胜。

端点级配置覆盖

通过 EndpointProperties.routingKeys 可按端点覆盖全局配置（见「配置方式」章节）。不同 Topic 可使用不同的路由键策略（如 im.chat 用 ["room"]，im.room 用 ["tenant", "room"]），但同一 Topic 的 PUSH/PULL 端点必须保持一致。

生产环境建议

🛡️
身份认证不可省略

URL 参数（?tenant=acme&room=lobby）和请求头（X-Room: lobby）均为纯声明，任何人可伪造。生产环境必须通过 AccessFilter 实现认证（如 JWT），确保身份不可篡改。

以下是一个最小可用的 JWT 认证过滤器示例：

Java 
@Component
@Order(10)
public class JwtAuthFilter implements AccessFilter {

    @Autowired
    private JwtService jwtService;

    @Override
    public void doFilter(AccessContext context, AccessFilterChain chain) {
        String token = context.getHeader("Authorization")
                .filter(h -> h.startsWith("Bearer "))
                .map(h -> h.substring(7))
                .orElseThrow(() -> new AccessDeniedException(
                        "Missing token", HttpStatus.UNAUTHORIZED));

        String userId = jwtService.parseUserId(token);
        context.setPrincipal(userId);  // 框架自动提取为 ConnectionMetadata.routingKey
        chain.doFilter(context);
    }
}

注册为 Spring Bean 后自动生效，无需额外配置。此时客户端的 SSE 连接改为通过请求头传 token：

JavaScript 
// fetch-based SSE 客户端（支持自定义请求头）
import { fetchEventSource } from '@microsoft/fetch-event-source';

await fetchEventSource('/api/chat/pull', {
  headers: { 'Authorization': 'Bearer eyJhbG...' },
  onmessage(ev) { console.log(JSON.parse(ev.data)); }
});

四层提取的优先级保证

当 AccessFilter 设置了 principal 后，框架优先使用该值作为 routingKey，URL 参数和 X-Me 头不会被触达。开发者无需关心兜底逻辑的冲突问题。
