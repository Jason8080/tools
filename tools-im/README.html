@RestController
public class ChatController {

    @Autowired
    private TopicRouter<Serializable, Msg> topicRouter;

    @PostMapping("/chat/send")
    public R<Long> sendMessage(@RequestBody ChatMessage chatMsg) {
        // 构建消息

            .topic("im.broadcast")
            .msg(chatMsg)
            .build();

        // 发布消息，返回消息 ID

        return R.ok(msgId);
    }
}

核心概念

理解 TOOLS IM 的核心抽象，快速构建自定义主题。

Topic（主题）

所有发布者和订阅者都通过主题字符串标识。框架通过主题名称匹配路由，忽略大小写。

Java 
// Topic 接口
public interface Topic extends Serializable {
    String topic();  // 返回主题标识
}

Publisher（发布者）

实现 Publisher 接口定义消息发布逻辑：

Java 
@Component
public class OrderPublisher implements Publisher<Long, OrderMsg> {

    @Override
    public String topic() {
        return "order.update";
    }

    @Override
    public Long push(MultiValueMap<String, String> urlParams, OrderMsg msg) {
        // 自定义发布逻辑（写入数据库、发送 MQ 等）
        return orderId;
    }
}

Subscriber（订阅者）

实现 Subscriber 接口定义消息订阅逻辑。注意 pull() 返回 Flux<MSG>，表示消息流：

Java 
@Component
public class OrderSubscriber implements Subscriber<OrderMsg> {

    @Override
    public String topic() {
        return "order.update";
    }

    @Override
    public Flux<OrderMsg> pull(MultiValueMap<String, String> urlParams) {
        // 返回消息流（SSE 场景）
        return sseConnectionManager.subscribe(topic())
                .map(TopicMessage::getMsg);
    }
}
💡
自动发现

只需将 Publisher 和 Subscriber 注册为 Spring Bean，TopicRouter 会自动发现并通过 topic() 匹配路由。无需手动注册。

TopicRouter（路由器）

TopicRouter 是核心路由组件，构造器注入所有 Publisher 和 Subscriber Bean，按主题名分派 push / pull 调用。

Java 
// TopicRouter 自动注入所有 Publisher 和 Subscriber
@Autowired
TopicRouter<Serializable, Msg> topicRouter;

// 发布消息
topicRouter.push("order.update", msg);

// 订阅消息（返回 Flux）
Flux<OrderMsg> flux = topicRouter.pull("order.update", params);

SSE 连接生命周期

每个 SSE 连接经历以下状态转换：

CREATED → ACTIVE → DRAINING → CLOSED
  • CREATED — 连接对象已创建，Flux 尚未被订阅
  • ACTIVE — Flux 已被订阅，连接正在收发数据
  • DRAINING — 排空中（Reaper / Shutdown 触发），等待自然关闭
  • CLOSED — 连接已关闭，资源已释放

三层清理机制

确保连接不泄漏的三道防线：

层级触发方式覆盖场景占比
第一层：doFinally 响应式回调 客户端主动断开、连接超时、正常完成 ~95%
第二层：Reaper 定时扫描（默认 30s） 僵尸连接（空闲超时）、过期连接 ~4%
第三层：Shutdown SmartLifecycle 关闭 应用关闭时强制清理所有连接 ~1%
⚠
并发安全

三层清理通过位域双守卫保证并发安全：单个 AtomicInteger 的 bit 0 竞争清理执行权，bit 1 保证计数器仅递减一次。

MQ 队列自动创建机制

框架利用 Spring Cloud Stream 的函数式绑定机制实现 MQ 基础设施的自动创建：

阶段触发时机自动/手动说明
Exchange 创建 首次 StreamBridge.send() ✅ 自动 Spring Cloud Stream 动态创建输出绑定，RabbitMQ 自动创建 Exchange
Queue 创建 Consumer Bean 注册后 ✅ 自动 RabbitMQ 自动创建 Queue 并绑定到 Exchange
Binding 映射 应用启动时 ❌ 手动 需配置 destination 将 Consumer 绑定到正确的 Topic
⚠️
关键配置：destination 映射

Consumer Bean 名称为 {topic}.consumer，Spring Cloud Stream 自动创建输入绑定 {topic}.consumer-in-0。但框架不会自动将此绑定与 destination 关联，需手动配置：

YAML 
spring:
  cloud:
    stream:
      bindings:
        # 发送端输出绑定（可选，默认使用 topic 名称）
        order.update:
          destination: order.update

        # 拉取端输入绑定（必须配置！）
        order.update.consumer-in-0:
          destination: order.update

高级功能

深入了解背压策略、连接清理、心跳、指标监听等高级特性。

背压策略

当消息发送速率超过客户端消费速率时，背压策略决定如何处理积压的消息。

drop-oldest（默认）

仅保留最新 1 条消息，旧消息被丢弃。适合实时性要求高、允许丢失的场景（如行情推送）。

buffer

缓冲指定数量的消息（默认 1024）。适合客户端能短暂吸收突发的场景（如日志流）。

error

零缓冲区，立即报错。适合严格要求不丢消息、需要客户端重连的场景。

按 Topic 覆盖策略

YAML 
im:
  sse:
    backpressure:
      default-strategy: drop-oldest        # 全局默认
      topic-overrides:
        order.update: buffer             # 订单 Topic 使用 buffer
        chat.message: error              # 聊天 Topic 使用 error
      topic-buffer-overrides:
        order.update: 2048               # 订单 Topic 缓冲区 2048

连接收割器（Connection Reaper）

定时扫描所有连接，检测并清理僵尸连接（空闲超过阈值）。

检测条件配置项默认值处理方式
空闲超时reaper.idle-timeout3600s标记 DRAINING → 等待 grace-period → 强制关闭
超过最大存活时间max-connection-lifetime24h通过 Flux.take(Duration) 自动终止
💡
心跳与 Reaper 的关系

心跳发送时会调用 conn.touch() 重置空闲计时器。因此活跃连接不会被 Reaper 误判为僵尸连接。心跳间隔（默认 30s）应小于 Reaper 空闲超时（默认 3600s）。

优雅关闭

SseConnectionManager 实现了 SmartLifecycle，应用关闭时自动执行以下流程：

  1. 拒绝新连接（accepting = false）
  2. 所有连接转换为 DRAINING 状态
  3. 向所有 Sink 发送完成信号
  4. 等待 drainTimeout（默认 30s），让连接自然关闭
  5. 强制关闭剩余连接
  6. 清理所有资源（Registry、Reaper、Metrics）
🔄
连接超时后的客户端行为

连接超过 maxConnectionLifetime 后，服务端发送 onComplete 关闭连接。客户端 EventSource 检测到断开后会自动重连（SSE 标准行为），建立新连接。

客户端集成

覆盖浏览器、Node.js 等主流客户端的集成方案和最佳实践。

浏览器 EventSource（基础用法）

使用浏览器原生 EventSource API：

JavaScript 
const eventSource = new EventSource('/pull/im.broadcast');

// 连接成功
eventSource.onopen = () => {
  console.log('SSE 连接已建立');
};

// 接收消息
eventSource.onmessage = (event) => {
  const message = JSON.parse(event.data);
  console.log('收到消息:', message);
};

// 错误处理
eventSource.onerror = (error) => {
  if (eventSource.readyState === EventSource.CONNECTING) {
    console.log('连接断开，正在自动重连...');
  } else if (eventSource.readyState === EventSource.CLOSED) {
    console.error('连接已关闭，不会自动重连');
  }
};
⚠
自动重连 vs 手动重试

自动重连（readyState = CONNECTING）：服务端发送 onComplete、网络中断恢复、服务端强制关闭 → EventSource 自动重连。
手动重试（readyState = CLOSED）：限流拒绝、服务不可用（HTTP 错误）→ 需要客户端代码手动重试。

带重试的 EventSource 封装

处理 HTTP 错误（限流、服务不可用）场景的健壮封装：

JavaScript 
function createResilientEventSource(url, options = {}) {
  const {
    maxRetries = Infinity,
    retryDelay = 3000,
    maxRetryDelay = 30000,
    onMessage,
    onOpen,
    onError
  } = options;

  let retryCount = 0;
  let currentDelay = retryDelay;
  let eventSource;

  function connect() {
    eventSource = new EventSource(url);

    eventSource.onopen = () => {
      console.log('SSE 连接成功');
      retryCount = 0;
      currentDelay = retryDelay;
      onOpen?.();
    };

    eventSource.onmessage = (event) => {
      onMessage?.(JSON.parse(event.data));
    };

    eventSource.onerror = (error) => {
      if (eventSource.readyState === EventSource.CLOSED) {
        // HTTP 错误（限流 / 服务不可用），手动重试
        retryCount++;
        if (retryCount <= maxRetries) {
          console.log(`将在 ${currentDelay}ms 后重试 (${retryCount}/${maxRetries})`);
          setTimeout(() => {
            eventSource.close();
            connect();
            currentDelay = Math.min(currentDelay * 2, maxRetryDelay);
          }, currentDelay);
        } else {
          console.error('SSE 重试次数已达上限');
          onError?.(error);
        }
      }
      // CONNECTING 状态会自动重连，无需处理
    };
  }

  connect();
  return {
    close: () => eventSource?.close(),
    getSource: () => eventSource
  };
}

// 使用示例
const sse = createResilientEventSource('/pull/im.broadcast', {
  maxRetries: 10,
  retryDelay: 3000,
  onMessage: (data) => console.log('消息:', data),
  onError: (err) => alert('连接失败，请刷新页面重试')
});

Node.js SSE 客户端

使用 fetch + ReadableStream 实现 Node.js SSE 客户端：

JavaScript 
async function connectSSE(url) {
  const response = await fetch(url, {
    headers: { 'Accept': 'text/event-stream' }
  });

  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  let buffer = '';

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;

    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split('\n');
    buffer = lines.pop() || '';  // 保留未完成的行

    for (const line of lines) {
      if (line.startsWith('data:')) {
        const data = line.slice(5).trim();
        console.log('收到消息:', JSON.parse(data));
      }
      // 忽略心跳注释（以 : 开头的行）
    }
  }
}

// 使用
connectSSE('http://localhost:8080/pull/im.broadcast');

监听 beforeunload 事件，调用 eventSource.close() 释放连接。

📊 重连监控

记录重连次数，超过阈值时告警。频繁重连可能表示服务端或网络问题。

🔒 消息幂等

重连可能丢失消息（drop-oldest 策略下）。客户端应通过消息 ID 实现幂等处理。

故障排查

常见问题诊断与解决方案。

常见问题

现象可能原因解决方案
SSE 连接无法建立 Topic 未注册（无 Publisher / Subscriber Bean） 确认 Publisher 和 Subscriber 已注册为 Spring Bean，且 topic() 返回值一致
SSE 连接无法建立 连接数达到上限 检查 im.sse.max-total-connections 和 im.sse.max-connections-per-topic，考虑扩容
消息未收到 Spring Cloud Stream binding 未配置 确认 RabbitMQ binder 已配置，imBroadcastConsumer-in-0 binding 正常
消息未收到 背压策略丢弃消息 默认 drop-oldest 策略会丢弃旧消息。如需保证消息不丢失，改用 buffer 策略
连接频繁断开 反向代理空闲超时 确认 Nginx proxy_read_timeout 大于心跳间隔（默认 30s）。建议设为 60s+
连接频繁断开 Reaper 误判为僵尸连接 确认心跳已启用（im.sse.heartbeat.enabled=true）。心跳会重置空闲计时器
连接数持续增长 客户端未正确关闭连接 确认页面卸载时调用 eventSource.close()。Reaper 最终会清理空闲连接
内存持续增长 动态 Topic 过多，计数器条目堆积 确认 im.sse.cleanup.compact-ttl 未设为 0，让 Reaper 定期压缩空 Topic 条目

监控建议

生产环境建议监控以下关键指标：

指标告警阈值说明
im.sse.connections.total> 80% max总连接数接近上限，考虑扩容
im.sse.subscribe.rate{result="REJECTED_*"}> 0有连接被拒绝，检查容量
im.sse.reaper.zombies持续增长僵尸连接增多，检查心跳配置
im.sse.errors> 0有异常发生，检查日志

日志级别

开发调试时开启 DEBUG 日志，排查连接生命周期细节：

YAML 
logging:
  level:
    cn.gmlee.tools.im: DEBUG      # 框架核心日志
    cn.gmlee.tools.im.sse: DEBUG  # SSE 连接管理日志
    cn.gmlee.tools.im.sse.cleanup: DEBUG  # Reaper 清理日志
🚨
性能提醒

DEBUG 日志在高连接数场景下会产生大量输出，仅用于开发调试。生产环境请使用 INFO 或 WARN 级别。
