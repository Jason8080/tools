框架定位

SseIm Framework 是即时通讯的基础设施，专注于消息的实时推送。它解决"如何把消息从服务端实时推送到客户端"，提供可插拔的 MQ 桥接和 SSE 推送能力。

⚙

配置驱动

3 行 YAML 配置 = 端点注册 + Stream 绑定 + SSE 连接管理。零 Java 代码开箱即用。

🔄

三段式解耦

进（Publisher）→ 转（Repeater）→ 出（Subscriber），每层职责单一、可独立替换，架构清晰可扩展。

🔀

双通道投递

广播（topicSink，O(1)）+ 定向（routingKeyIndex + directedSink，O(K)），统一两种投递模式。

doFinally（95%）+ Reaper（4.9%）+ maxLifetime（0.1%），保证连接不泄露。

核心组件

📋

EndpointRegistry

端点注册表。存储 path → topic + mode 映射，支持运行时动态增删。

🛣

EndpointRouter

动态路由器。RouterFunction 实现，按 mode 分发 PUSH / PULL 请求，织入 AccessFilter 链。

🏭

TopicRegistry

Topic 组件注册表。通过工厂模式按需创建 Publisher / Repeater / Subscriber。

📤

Publisher

消息发布器（进）。接收 POST 请求，构建 TopicMessage 经 Repeater 发送到 MQ。

🔄

Repeater

消息转发器（转）。桥接 MQ 两端，send → MessageSender，receive → 拦截器链 → SSE 推送。

📥

Subscriber

消息订阅器（出）。构建带生命周期钩子的 Reactor Flux，交付 SseConnectionManager 推送。

📱

SseConnectionManager

SSE 连接管理器。连接注册/注销、背压策略、心跳保活、定时清理、优雅关闭。

💾

SseConnectionRegistry

连接存储与索引。管理双通道架构（topicSink + directedSink），维护 routingKeyIndex 反向索引。

♻

TopicLifecycleManager

Topic 生命周期管理。状态机（CREATED → ACTIVE → DESTROYING → DESTROYED）、引用计数、自动清理空闲 Topic。

🔍

ConnectionReaper

连接收割器。三层清理的第二层，定时扫描僵尸连接（30s），异步强制关闭，防止资源泄露。

🧭

RoutingKeyComposer

路由键组合策略。双通道投递的核心，支持广播和按 routingKey 定向投递，可自定义路由规则。

📨

MessageSender

隔离核心架构与中间件实现。支撑 CLUSTER（MQ 传输）与 STANDALONE（直连）双模式部署，实现架构与基础设施的彻底解耦。

JavaScript (微信小程序) 
/**
 * 微信小程序 SSE 客户端（基库 2.20.2+）
 * 通过 wx.request + enableChunked 模拟 EventSource
 *
 * 社区无成熟第三方 SDK（现有库 stars 均 < 20，无生产验证），
 * 此为推荐实现：零依赖，含断线指数退避重连。
 */
class SseClient {
  constructor({ url, headers = {}, onMessage, onOpen, onError, onReconnect }) {
    this.url = url;
    this.headers = headers;
    this.onMessage = onMessage;
    this.onOpen = onOpen;
    this.onError = onError;
    this.onReconnect = onReconnect;
    this.buffer = '';
    this.task = null;
    this.lastEventId = '';       // 最近 id: 字段，重连时作 Last-Event-ID
    this.retryMs = 3000;         // 默认重连间隔 3s，可被服务端 retry: 覆盖
    this.retries = 0;
    this.maxRetries = 10;
    this.closed = false;
  }

  connect() {
    if (this.closed) return;
    const headers = { ...this.headers, 'Accept': 'text/event-stream' };
    if (this.lastEventId) headers['Last-Event-ID'] = this.lastEventId;

    this.task = wx.request({
      url: this.url,
      method: 'GET',
      enableChunked: true,
      header: headers,
      success: () => { this.retries = 0; this.onOpen?.(); },
      fail: (err) => {
        this.onError?.(err);
        this.scheduleReconnect();
      }
    });

    this.task.onChunkReceived((res) => {
      this.buffer += this.decodeChunk(res.data);
      this.parseEvents();
    });
  }

  decodeChunk(buf) {
    return new TextDecoder('utf-8').decode(new Uint8Array(buf));
  }

  parseEvents() {
    const parts = this.buffer.split('\n\n');
    this.buffer = parts.pop() || '';
    for (const block of parts) {
      let data = '', event = 'message', id = '', retry = null;
      for (const line of block.split('\n')) {
        if (line.startsWith('data:'))    data   += line.slice(5).trim() + '\n';
        else if (line.startsWith('event:')) event = line.slice(6).trim();
        else if (line.startsWith('id:'))    id   = line.slice(3).trim();
        else if (line.startsWith('retry:')) retry = parseInt(line.slice(6).trim(), 10);
      }
      if (retry > 0) this.retryMs = retry;      // 服务端指定重连间隔
      if (id) this.lastEventId = id;
      if (data) this.onMessage?.({ data: data.trim(), event, id });
    }
  }

  scheduleReconnect() {
    if (this.closed || this.retries >= this.maxRetries) return;
    const delay = Math.min(this.retryMs * 2 ** this.retries, 30000);
    this.retries++;
    this.onReconnect?.(this.retries, delay);
    setTimeout(() => this.connect(), delay);
  }

  close() {
    this.closed = true;
    this.task?.abort();
    this.task = null;
  }

  reconnect() {
    this.close();
    this.closed = false;
    this.retries = 0;
    this.buffer = '';
    this.connect();          // 自动带上 Last-Event-ID 续传
  }
}

// ====== 使用示例（Page 生命周期集成）======
Page({
  data: { messages: [] },

  onReady() {
    this.sse = new SseClient({
      url: 'https://api.example.com/api/chat/pull?tenant=acme&room=lobby',
      headers: { 'Authorization': 'Bearer <token>' },
      onMessage: (e) => {
        const msg = JSON.parse(e.data);
        this.setData({ messages: [...this.data.messages, msg] });
      },
      onError:     (e) => console.error('SSE 错误:', e),
      onReconnect: (n, d) => console.log('第 ' + n + ' 次重连，' + d + 'ms 后')
    });
    this.sse.connect();
  },

  onHide() {
    // 页面隐藏（进入后台 / 跳转其他页面）→ 关闭连接节省资源
    this.sse?.close();
  },

  onShow() {
    // 页面重新显示 → 重连恢复消息流（Last-Event-ID 续传）
    this.sse?.reconnect();
  },

  onUnload() {
    // 页面卸载 → 彻底释放
    this.sse?.close();
    this.sse = null;
  }
});

起源背景

从真实生产故障中提炼根因，针对性地选择更合适的技术方案。

从生产问题出发

SseIm Framework 不是"为了用新技术而换架构"，而是从两个真实的生产故障中提炼出了根因，然后针对性地选择了更合适的技术方案。

🔥

竞价板块：连接泄露

原架构 WebSocket + STOMP + RabbitMQ。客户端连接管理不当，导致连接泄露 — 连接数只增不减，直到内存溢出，引发生产故障。

🐢

站内信板块：消息卡顿/超时

原架构同样是 WebSocket + STOMP + RabbitMQ。消息发送非常卡顿、缓慢，甚至超时，用户体验极差。

两个板块的问题表象不同，但根因指向同一个方向：WebSocket 的连接模型不适合这些场景。

WebSocket 的两个经典陷阱

陷阱一：连接泄露（竞价板块的根因）

WebSocket + STOMP 的连接模型是有状态长连接，服务端需要自己管理连接的生命周期。一旦客户端异常断开（网络波动、页面崩溃、移动端切换后台），如果清理逻辑有任何遗漏，连接就会残留在内存里 — 只增不减，直到 OOM。

这不是个别问题，WebSocket 连接泄露是业界非常常见的生产事故根因。

陷阱二：协议过重（站内信板块的根因）

STOMP 的消息投递模型是双向的，但站内信场景本质上是服务端单向推送。用 WebSocket + STOMP 做单向推送，是在用最重的协议做最简单的事，不必要的协议开销和连接管理复杂度都会变成性能瓶颈。

核心洞察：IM 不需要"双向长连接"

💡
即时通讯的真实模型

虽然 SSE 是单向通道，但大部分即时通讯场景其实只需要单向通道。因为消息发送是用户实时触发的离散动作，只需要能发出去即可，HTTP 才是简单又可靠的方案。

大多数人对 IM 的直觉是"需要双向通道"，所以第一反应就是 WebSocket。但仔细拆解用户行为：

方向行为特征本质最优协议
客户端 → 服务端（发消息） 用户点"发送"按钮 → 一次 HTTP POST → 结束 离散动作，用完即走 HTTP POST
服务端 → 客户端（收消息） 持续等待服务端主动推送 持续等待，需要长连接 SSE

两个方向用各自最合适的协议，而不是用 WebSocket 把两个方向绑在同一条连接上。

WebSocket 的问题在于"过度对称"

WebSocket 提供的是对称的双向长连接，但 IM 的两个方向根本不是对称的：

  • 发消息是一次性的 HTTP 请求，不需要长连接
  • 收消息需要持续等待，需要长连接

用 WebSocket 做 IM，相当于为了"服务端能推送"这个需求，被迫把"客户端发消息"也绑进了一条长连接里。然后就要自己处理：

  • 这条连接上的消息协议（STOMP 帧解析）
  • 这条连接的状态管理（心跳、重连、断线恢复）
  • 这条连接的生命周期（谁负责关闭、怎么清理）

复杂度全是你自己加的，而 HTTP +　SSE 方案里，这些复杂度本来就不存在。

SseIm 的解法：按需分配连接

按需分配 vs 永远占用
✅ SseIm：按需分配
  • 需要推送时 → 建立 SSE 连接（长连接）
  • 需要发消息时 → 发一个 HTTP 请求（用完即释放）
  • 不需要推送时 → 没有任何连接占用
❌ WebSocket：永远占用
  • 永远占着一条双向连接
  • 发消息、收消息、心跳全在同一连接上
  • 连接管理复杂度全部自己承担

原方案 vs 新方案对比

维度WebSocket + STOMPHTTP + SSE
连接模型 有状态双向长连接，服务端维护连接状态机 HTTP 短连接 + SSE 单向长连接，HTTP 层天然感知断连
连接泄露风险 高 — 依赖应用层心跳探测，清理逻辑遗漏即泄露 低 — 三层清理机制兜底（doFinally → Reaper → maxLifetime）
协议开销 重 — STOMP 帧解析、双向握手、连接状态维护 轻 — HTTP + SSE 原生支持，零额外协议开销
消息延迟 高 — 协议栈层次多，处理链路长 低 — 最短消息路径，直接 SSE 推送
客户端依赖 需要 STOMP 客户端 SDK 浏览器原生 EventSource，零依赖
扩展性 直接绑定 RabbitMQ Spring Cloud Stream 抽象，可换任意 MQ
🎯
架构决策的本质

不是在"选 SSE 还是 WebSocket"，而是在想清楚消息推送的本质是单向的之后，做出的必然选择。用 Spring Cloud Stream 而不是直接绑死某个 MQ，在解决当前问题的同时保留了架构的灵活性 — 以后换 MQ 不需要改业务代码。

设计路径

SseIm Framework 的诞生遵循一条清晰的路径：

生产故障暴露根因

竞价板块连接泄露（OOM）、站内信板块消息卡顿/超时。两个板块的问题都指向 WebSocket + STOMP 的架构缺陷。

三层清理机制

SSE 连接生命周期由三层清理机制共同管理，每层职责不同，协同保证连接不泄露：

L1

🛡 doFinally（响应式清理）

客户端主动断开 / 网络中断 / 错误 / 完成

被动响应
目标：释放资源
占比：~95%
客户端感知：✅ 立即
L2

🔍 Reaper 空闲检查（自然完成）

空闲超时（默认 3600s）· 基于 lastActivityAt

自然完成
目标：让客户端感知并重连
占比：~4.9%
客户端感知：✅ 立即
关闭方式：tryEmitComplete() 不用 cancel()，让 Flux 的 complete 信号正常传播到客户端，EventSource 自动重连
L3

⏰ Reaper 过期检查（强制关闭）

超过最大存活时间（默认 24h）· 基于 createdAt

强制关闭
目标：防止连接泄漏
占比：~0.1%
客户端感知：⚠ 强制断开
关闭方式：使用 cancel() 强制终止 Flux，确保长期存活的连接被立即关闭，防止资源泄漏
层级 触发条件 时间基准 关闭方式 设计目标
L1 doFinally 客户端断开 / 错误 / 完成 无（事件驱动） 被动清理 释放资源
L2 Reaper 空闲 空闲超时（3600s） lastActivityAt 自然完成（不用 cancel） 让客户端感知并重连
L3 Reaper 过期 超过最大存活时间（24h） createdAt 强制关闭（用 cancel） 防止连接泄漏
💡
为什么 L2 和 L3 关闭方式不同？

L2 空闲清理的目标是"让客户端感知并重连"，所以使用自然完成（tryEmitComplete），客户端收到 onComplete 信号后 EventSource 自动重连。L3 过期清理的目标是"防止连接泄漏"，所以使用强制关闭（cancel()），确保长期存活的连接被立即终止。

🔄
优先级

在 ConnectionReaper.scan() 中，过期检查（L3）优先于空闲检查（L2）。过期连接必须强制关闭，不应该再等待 gracePeriod。

Topic 作为资源管理基本单元

Topic 是框架的基本资源管理单元，从消息发布到 SSE 推送的整条链路上，所有中间组件都是 Topic 级别的资源。

全链路资源归属

🏭 逻辑层资源（每个 Topic 一份）

  • Publisher — 消息发布器
  • Repeater — 消息转发器
  • Subscriber — 消息订阅器

🔌 物理层资源（CLUSTER 模式）

  • Spring Cloud Stream binding 配置
  • Consumer Bean 定义
  • RabbitMQ 连接（由 Spring 管理）

📡 连接层资源（每个 Topic 一份）

  • topicSinks — 广播消息 Sink
  • topicConnections — 连接 ID 集合
  • routingKeyIndex — 定向路由索引

资源生命周期

事件创建的资源清理的资源
首个连接/消息 全链路资源（Publisher + Repeater + Subscriber + Sink + 路由索引） —
Topic 变空 — 等待 emptyTopicTtl（默认 60s）
超时清理 — 全链路资源（逻辑层 + 物理层 + 连接层）
⏰
计时起点

从最后一个连接离开时开始计时，而非从最后一条消息开始。

防抖动设计：使用 putIfAbsent 记录首次变空时间。如果 Topic 短暂恢复连接后再次变空，不会重置计时器，确保超时后必然被清理。

示例：

  • 10:00:00 - 最后一个连接断开，Topic 变空 → 记录时间戳 10:00:00
  • 10:00:30 - 新连接加入（30s < 60s TTL）→ 复用资源，从 emptyTopics 移除
  • 10:01:00 - 连接断开，Topic 再次变空 → 不重置计时器，仍按 10:00:00 计算
  • 10:01:01 - 超过 60s TTL，触发清理
💡
设计优势
  • 资源隔离：每个 Topic 独立管理，一个 Topic 的清理不影响其他 Topic
  • 简化清理：通过 Topic 名称即可定位和清理所有相关资源
  • 生命周期一致性：Topic 创建时创建所有资源，销毁时清理所有资源

静态 Topic vs 动态 Topic

类型特点资源策略示例
静态 Topic 固定数量，长期存在 可配置为"永不清理"，避免首个用户负担 im.chat、im.notification
动态 Topic 按需创建，数量不固定 必须启用自动清理，防止内存泄漏 user.{userId}、session.{sessionId}

Spring Cloud Stream 限制说明

⚠
重要：Topic 销毁的架构约束

Spring Cloud Stream 的 BindingService 不提供 unbind() API，已创建的 Consumer/Producer binding 无法通过编程方式销毁。

具体影响

操作行为说明
Topic 销毁 清理配置 + Bean 定义 + 内部记录 实际的 RabbitMQ 连接会保留到应用重启
Topic 重建 创建新的配置和 Bean 复用已有的 MQ 连接，不会创建新连接
内存泄漏 不会发生 框架清理所有内部引用，MQ 连接由 Spring 管理

设计权衡

💡
为什么这样设计？

Topic 通常是长期存在的：IM 场景下，Topic 对应业务频道（如聊天室），生命周期与应用一致，很少需要销毁。

动态 Topic 场景：如果确实需要频繁创建/销毁 Topic，建议使用单机模式（无 MQ 依赖），或接受 MQ 连接保留到重启的约束。

监控支持：通过 /im/admin/topics/lifecycle API 可查询 Topic 状态，区分"逻辑销毁"和"物理销毁"。

可靠性保障：内置重试机制

多线程并发 tryEmitNext() 时，CAS 竞争可能导致消息丢失（返回 FAIL_NON_SERIALIZED）。框架提供内置重试策略，通过策略模式支持四种重试机制：

  • no-retry（默认）：单次尝试，性能最优，适合单线程发布场景
  • busy-loop：忙等待重试直到成功或超时，可靠性最高
  • bounded：固定次数重试，平衡可靠性和资源消耗
  • exponential-backoff：指数退避重试，适合高并发竞争场景

配置示例：

im:
  sse:
    emit-retry:
      default-strategy: busy-loop  # 默认策略
      busy-loop-timeout: 100ms     # 超时时间
      topic-overrides:
        im.chat: bounded           # 按 Topic 覆盖策略

静态 Topic 永不清理配置（可选）

对于静态 Topic（固定数量、长期存在），可配置为"永不清理"，避免首个用户承担资源创建开销。

YAML 
im:
  sse:
    cleanup:
      empty-topic-ttl: 36500d  # 100 年，实际上永不清理
      compact-ttl: 36500d      # 同时禁用计数器压缩
⚠
⚠️ 重要：仅适用于静态 Topic

适用场景：固定数量的业务 Topic（如 im.chat、im.notification），资源创建后永久保留。

不适用场景：动态 Topic（如 user.{userId}、session.{sessionId}），会导致内存持续增长。

内存影响：每个空 Topic 占用 ~5 KB，100 个静态 Topic 仅占用 ~500 KB（可忽略）。

    cleanup:
      empty-topic-ttl: 24h  # 保留 24 小时
      compact-ttl: 7d      # 计数器保留 7 天

效果：日间流量波动时资源复用，夜间空闲时资源保留到第二天，长期不用的 Topic 在 24 小时后清理。

定向投递

基于地址模型的精准投递 — 同一套寻址语义，双通道互斥架构，O(K) 精准投递。

快速体验（零 Java 代码）

以聊天室为例。假设已配置 /api/chat/push（PUSH）和 /api/chat/pull（PULL），全局 routing-keys: ["room"]：

alice 和 bob 加入 lobby 房间

JavaScript 
// 浏览器原生 EventSource — URL 参数即地址
const es = new EventSource('/api/chat/pull?room=lobby');
es.onmessage = e => console.log('收到:', JSON.parse(e.data));

两人的连接地址均为 "room=lobby"。不同房间（?room=main）的连接互不干扰。

发送消息到 lobby 房间 — 仅 alice 和 bob 收到

HTTP 
# 相同参数格式 → 相同 routingKey → 精准命中
POST /api/chat/push?room=lobby
Content-Type: application/json

{"from": "charlie", "content": "大家好"}

alice 和 bob 同时收到。/api/chat/push 不带参数时则为广播，所有连接收到。

✅
就这么简单

订阅方和发布方使用相同的 URL 参数格式，框架自动完成地址建立、索引构建、精准投递。无需手写路由逻辑，无需额外依赖。下面逐步展开其工作原理。

核心概念

定向投递建立在对称寻址模型上 — 订阅方声明地址，发布方指定目标，框架负责匹配：

概念载体语义类比
地址（Address）ConnectionMetadata.routingKey订阅方的通信地址 —「消息送到哪里」公寓房号
目标（Target）TopicMessage.routingKeys发布方的投递目标集合 —「发给哪些地址」快递单上的收件地址列表

匹配规则：目标的某个元素等于连接的地址时，消息投递到该连接。routingKeys 为空 → 广播（所有连接收到）；非空 → 定向（仅匹配的连接收到）。

💡
对称设计

同一套 RoutingKeyComposer 同时用于订阅方的地址建立和发布方的目标提取 — 不是两套独立逻辑的拼接，而是一个模型的两侧投影。这从结构上保证了双方寻址语义的一致性。

寻址 API

两种路径，殊途同归 — 最终都生成 TopicMessage.routingKeys：

路径 A — HTTP 端点（零 Java 代码）

使用与订阅方相同的 URL 参数格式，框架自动提取 routingKey：

JavaScript

路径 B — Java API（服务端内部调用）

注入 RoutingKeyComposer 构建 routingKey，保证与 HTTP 路径格式一致：

Java 
@Autowired
private TopicRegistry topicRegistry;

@Autowired
private RoutingKeyComposer composer;

// 定向投递 — Composer 构建 routingKey，与 HTTP 路径格式一致
public void sendToRoom(String room, ChatMsg msg) {
    MultiValueMap<String, String> params = new LinkedMultiValueMap<>();
    params.add("room", room);
    Set<String> targets = composer.extractRoutingTargets(null, params);

    TopicMessage<ChatMsg> envelope = TopicMessage.<ChatMsg>builder()
            .topic("im.chat")
            .msg(msg)
            .routingKeys(targets)
            .build();
    topicRegistry.ensureRepeater("im.chat").send(envelope);
}

// 批量投递
public void sendToRooms(Set<String> rooms, ChatMsg msg) {
    MultiValueMap<String, String> params = new LinkedMultiValueMap<>();
    rooms.forEach(room -> params.add("room", room));
    Set<String> targets = composer.extractRoutingTargets(null, params);

    TopicMessage<ChatMsg> envelope = TopicMessage.<ChatMsg>builder()
            .topic("im.chat")
            .msg(msg)
            .routingKeys(targets)
            .build();
    topicRegistry.ensureRepeater("im.chat").send(envelope);
}

等价性保证

HTTP 路径和 Java API 共用同一个 RoutingKeyComposer — 相同的输入必然产生相同的 routingKey。两条路径只是入口不同，底层寻址逻辑完全一致。

路由键机制

理解了用法，现在看框架如何建立和管理路由键。

地址建立（routingKey 提取）

每个 SSE 连接都携带一个地址标识（routingKey）。框架按四层优先级自动提取：

优先级来源适用场景示例
① AccessFilter 设置的 principal（String） 生产环境 — JWT / OAuth JWT Filter → setPrincipal("user-123")
② PrincipalRoutingKeyConverter 从复杂 principal 提取 principal 为对象（如 UserDetails） UserDetails.getUsername()
③ X-Me 请求头 服务端调用、测试工具 curl -H 'X-Me: user-123' ...
④ URL 参数按 routing-keys 配置组合 浏览器 EventSource（无法自定义请求头） EventSource('/pull?room=lobby')
⚠️
安全提示

③④ 层（URL 参数、X-Me 头）均为纯声明，无认证能力，仅用于开发调试。生产环境应通过 ① 层 AccessFilter 实现 JWT 认证，确保地址不可伪造。详见「生产环境建议」。

地址格式

routingKey 格式为规范化查询字符串：key 按字母排序，key=value 以 & 拼接。保证参数顺序无关性：

?room=lobby              →  "room=lobby"（单键）
?tenant=acme&room=lobby  →  "room=lobby&tenant=acme"（key 字母排序）
?room=lobby&tenant=acme  →  "room=lobby&tenant=acme"（相同结果，顺序无关）
无参数                    →  null（广播连接，不参与定向索引）

routingKey 生命周期

routingKey 贯穿投递全链路：

  • 订阅时：Composer 从 URL 参数组合 routingKey → 存入 ConnectionMetadata → 注册到反向索引（routingKeyIndex）
  • 发布时：同一 Composer 从 URL 参数提取目标集合 → 通过反向索引 O(K) 定位目标连接
  • MQ 桥接：routingKeys 随 TopicMessage 作为不可变载荷完整保留，支持跨服务定向路由
⚠️
匹配约束

同一 Topic 的 PUSH/PULL 端点必须使用相同的 routing-keys 配置，确保双方生成的 routingKey 格式完全一致。可全局配置 im.sse.routing-keys，也可通过 EndpointProperties.routingKeys 按端点覆盖。

优雅关闭（SmartLifecycle）

SseConnectionManager 实现 SmartLifecycle 接口，支持应用关闭时优雅地排空 SSE 连接：

关闭流程

🛑

阶段 1：拒绝新连接

设置 accepting=false，新订阅请求返回 503

⏳

阶段 2：排空现有连接

异步 drain 现有连接，等待客户端自然断开

✅

阶段 3：强制关闭

超时后强制关闭剩余连接，确保资源释放

配置参数

YAML 
im:
  sse:
    shutdown:
      grace-period: 30s      # 排空等待时间
      force-close: true       # 超时后是否强制关闭
      propagate-interrupt: true # 是否传播中断信号
💡
生产部署建议

配合 Kubernetes 的 terminationGracePeriodSeconds 使用，确保应用有足够时间排空连接。

示例：设置 terminationGracePeriodSeconds: 60 + im.sse.shutdown.grace-period: 30s

故障排查

常见问题诊断与解决方案。

常见问题

现象可能原因解决方案
SSE 连接无法建立 端点未配置 检查 im.endpoints 配置，确认 mode: pull 的端点存在
消息未收到 RabbitMQ binding 未创建 查看启动日志中 [TopicResourceFactory] 相关日志，确认 binding 已创建
连接频繁断开 反向代理空闲超时 确认 Nginx proxy_read_timeout 大于心跳间隔（默认 30s）
连接数持续增长 客户端未正确关闭连接 确认页面卸载时调用 eventSource.close()。Reaper 会清理空闲连接
